# 企画フェーズ

書籍の目次構成、各章のアウトライン、読者の学習パスを設計し、Markdownファイルの骨格を生成する。

## 手順

### 1. ヒアリング

以下の項目をユーザーに確認する:

| 項目 | 説明 |
|------|------|
| テーマ | 書籍が扱う技術領域・主題 |
| 対象読者 | 読者の前提知識・レベル（初心者、中級者、上級者） |
| ゴール | 読者が本書を読み終えた後に達成できること |
| 想定分量 | 大まかなページ数・章数の希望（なければ目安を提案） |
| 演習の有無 | 章末問題、ハンズオン演習、プロジェクト課題等を含めるか |

### 2. 全体構成の設計

以下の観点で目次構成を設計する:

**構成パターン**（書籍の性質に応じて選択）:

| パターン | 特徴 | 適する書籍 |
|---------|------|-----------|
| 段階的導入型 | 基礎→応用→発展と段階的に進む | 入門書、チュートリアル型 |
| リファレンス型 | 機能・トピック別に独立した章 | API解説、設定ガイド |
| プロジェクト型 | 実際のプロジェクトを段階的に構築 | ハンズオン・実践書 |
| 試験対策型 | ドメイン別解説＋模擬試験 | 資格試験対策本 |

**設計の目安**:
- 章の分量はトピックに必要な量だけ書く（行数の目安を目標にしない）
- 章数はトピック数に応じて決める
- 各章は可能な限り独立して読めるようにする
- 章の前後関係が必要な場合は、依存関係を明示する

### 3. 各章のアウトライン作成

各章について以下を定義する:

```
## 第N章: <章タイトル>

**目的**: この章で読者が学ぶこと
**扱わないこと**: 関連するが本章では扱わないトピック（担当章を明記。例: トークン実装→第5章）
**前提**: 先に読んでおくべき章（あれば）
**想定行数**: NNN行

### N.1 <セクション名>
- 扱う内容の箇条書き

### N.2 <セクション名>
- 扱う内容の箇条書き

### 章末演習（任意）
- 演習問題の概要
```

### 4. 読者の学習パスの確認

- 難易度が段階的に上がっているか
- 前の章の知識が後の章で活用されているか
- 各章の分量バランスが適切か
- 重複する内容がないか
- 各章の「扱わないこと」に記載されたトピックが、いずれかの章の「目的」でカバーされているか（漏れの検出）

### 5. ユーザーへの提示と承認

設計した目次構成を提示し、ユーザーの承認を得る。フィードバックがあれば修正する。

### 6. Markdownファイルの生成

承認後、`src/` 配下にMarkdownファイルを生成する:

- 各章ファイルにはH1（章タイトル）とH2（セクション見出し）の骨格を含める
- 本文は未記入（後の write フェーズで執筆）
- まえがき・謝辞・あとがきはユーザーが明示的に要求した場合のみ生成する
- 最終章の末尾に書籍全体のまとめ（各章の要点を箇条書きで総括）を含める

**ファイル生成例**:

```markdown
# 第1章 はじめに

## 1.1 本書の対象読者

## 1.2 本書の構成

## 1.3 開発環境の準備
```

同時に、`src/.chapter-registry.md` を生成する。各章のplan情報を転記し、writeフェーズでの重複防止に使う:

```markdown
# チャプターレジストリ

> 各章の執筆完了時に更新される。次章の執筆時にこのファイルを読み、
> 用語の重複定義や内容の重複を防ぐ。

## 第1章: はじめに
- **状態**: 未執筆
- **扱う予定のトピック**: （planで定義した目的・セクション内容から転記）
- **扱わないこと**: （planの除外トピックから転記）

## 第2章: ...
（全章分を記載）
```

### 7. コミット

```bash
git add src/
git commit -m "✨ 目次構成と章の骨格を追加"
```

注: `src/.chapter-registry.md` もコミットに含まれる。ビルドスクリプトはドットファイルを自動除外するためEPUBには含まれない。

### 9. 完了メッセージ

目次構成が完了したことを報告し、次のステップ（`/book-writing write` で各章の執筆）を案内する。各章の執筆順序について推奨がある場合は併せて伝える。
