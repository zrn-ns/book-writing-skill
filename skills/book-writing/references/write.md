# 執筆フェーズ

章のアウトラインに基づいて本文を執筆する。品質基準を遵守し、章間の整合性を保つ。

## 手順

### 1. 対象章の特定

ユーザーの指示から執筆対象の章を特定する。

- 「第3章を書いて」→ `src/` 内の該当ファイルを特定
- 「次の章を書いて」→ 未執筆の次の章を特定（H1/H2骨格のみのファイル）
- 「全部書いて」→ 未執筆の章を順番に執筆

### 2. コンテキストの収集

執筆前に以下を確認する:

1. **チャプターレジストリ**: `src/.chapter-registry.md` を読み、全章の執筆状況を把握する:
   - どの章が執筆済みか
   - どの用語がすでに定義済みか
   - 各章が扱った概念と扱わないと決めたトピック
2. **対象章のアウトライン**: 既存のH1/H2骨格を読み込む
3. **直前の章の本文**: 直前の1章を読み、文体・トーンの一貫性を確認
4. **後の章のアウトライン**: 後続の章で扱う予定のトピックを確認（重複回避）
5. **book.yaml**: 書籍のメタデータ（タイトル、テーマ）を確認
6. **CLAUDE.md**: プロジェクト固有のルールを確認

### 3. 執筆

アウトラインの骨格（H1/H2）を維持しつつ、本文を執筆する。

**執筆の原則**:

- **要点ファーストで書く**: 結論や定義を先に示し、補足は後に置く
- **既知の前提を繰り返さない**: 読者はテーマの基礎知識を持っている前提で書く
- **具体例は必要最小限にする**: 概念の理解に不可欠な例だけを添える
- **コード例は動作可能に**: 読者がコピー＆ペーストで試せるコードを書く
- **冗長さを避ける**: 1つの概念に対して複数の表現で繰り返し説明しない
- **教科書的な語りを避ける**: 「〜を見ていきましょう」「〜について考えてみます」のような誘導文は省く

**文体の統一**:

- ですます調で統一（技術書の標準）
- 読者への呼びかけは「あなた」ではなく「読者」または省略
- 能動態を優先（「〜されます」より「〜します」）
- 「〜することができます」→「〜できます」に短縮する
- 主語の過剰明示を避ける（日本語は主語省略が自然）
- 接続詞の多用を避ける（文の順序で論理を伝える）
- 定型評価語（「〜と言えるでしょう」「注目に値する」等）を使わず、断定または具体的事実で書く

### 4. 品質チェック

執筆後、以下のチェックリストを適用する:

#### EPUB互換性
- [ ] `<details>`, `<summary>`, `<iframe>` 等のHTMLタグを使用していない
- [ ] コードブロックに言語指定が付いている（```python 等）
- [ ] 見出し階層が正しい（H1 → H2 → H3、飛ばしなし）

#### 技術的正確性
- [ ] コード例が構文的に正しい
- [ ] API名、関数名、パラメータ名が正確
- [ ] バージョン情報が最新（または明示的にバージョンを記載）

#### 章間整合性
- [ ] 前の章で説明済みの概念を不要に再説明していない
- [ ] 前の章で説明済みの用語と同じ表記を使用している
- [ ] 「第N章で述べた〜」等の前方参照が正確
- [ ] 「第N章で詳述する」等の後方参照の章番号が正しい
- [ ] 難易度が前の章から適切に向上している
- [ ] チャプターレジストリの「扱わないこと」に記載されたトピックを本章で扱っていない（境界の遵守）

#### 読者体験
- [ ] 章の冒頭に扱うトピックの概要がある
- [ ] 専門用語の初出時に英語併記がある
- [ ] 長いセクションには適切な区切り（サブセクション、水平線）がある
- [ ] 章末に要点の要約がある
- [ ] 章末に次章への橋渡しがある（最終章を除く。次章で扱うトピックへの接続を1〜2文で示す）

#### 日本語文体（AI臭さの排除）
- [ ] 定型評価語を使っていない（「〜と言えるでしょう」「今後の展開が注目されます」「重要な示唆を与えている」「注目に値する」→ 断定するか削除）
- [ ] `**ラベル:** 内容` 形式の箇条書きを使っていない（ラベルを消して内容だけにする）
- [ ] 説教くさい前置きがない（「ここで重要なのは」「注意すべき点として」「〜について理解しておく必要があります」→ 前置きを消して内容を直接書く）
- [ ] 接続詞を多用していない（「一方で」「しかしながら」「加えて」「このように」「さらに」「とりわけ」が1セクション内に3回以上出たら半分削除）
- [ ] 主語を過剰に明示していない（「このツールは〜。このツールは〜。」→ 主語を省略して自然な日本語にする）
- [ ] 「〜することができます」を使っていない（→「〜できます」に短縮）
- [ ] 意義を過剰に強調していない（「極めて重要」「計り知れない」→ 具体的な事実・数字に置き換える）
- [ ] 章の冒頭がテンプレ文で始まっていない（「近年、〜が急速に進展しており」→ 具体的な事実や場面から始める）
- [ ] 章の結論がテンプレ文で終わっていない（「〜が期待されます」「〜と考えられます」→ 具体的な次のアクションや明確な結びで終える）

### 5. チャプターレジストリの更新

`src/.chapter-registry.md` の該当章を更新する:

```markdown
## 第N章: <章タイトル>
- **状態**: 執筆済み
- **扱った概念**: 実際に章で解説した概念のリスト
- **定義した用語**: 初出で定義・説明した技術用語
- **読者が得た前提知識**: 後続章が前提にできる知識
- **扱わないこと**: （planの除外トピックを維持）
```

### 6. ビルド確認

執筆が完了したら、ビルドを実行してEPUBが正常に生成されることを確認する:

```bash
deno run --allow-run --allow-read --allow-write <このスキルの scripts/build.ts の絶対パス>
```

### 7. コミット

意味のある単位でコミットする:

```bash
git add src/<対象ファイル> src/.chapter-registry.md
git commit -m "✨ 第N章: <章タイトル> を執筆"
```

章が長い場合は、セクション単位で段階的にコミットしてもよい（レジストリの更新は最後のコミットに含める）:

```bash
git commit -m "✨ 第N章: 基本構造とセクションN.1-N.3を執筆"
git commit -m "👍 第N章: セクションN.4-N.6と章末演習を追加"
```

### 8. 完了報告

執筆した章の概要を報告する:
- 行数
- セクション数
- 含まれるコード例の数
- 含まれる演習問題の数（あれば）
- 次に執筆すべき章の提案
