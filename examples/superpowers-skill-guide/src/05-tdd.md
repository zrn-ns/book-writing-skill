# 第5章 test-driven-development

TDDスキルが強制するRED-GREEN-REFACTORサイクルと、違反検出の仕組み。

## 5.1 RED-GREEN-REFACTORの強制

### 鉄則

```
失敗するテストなしに本番コードを書かない
```

テストより先にコードを書いた場合は「削除してやり直す」が唯一の正解です。「参考として残す」「テストを書きながら合わせる」は禁止で、deleteはdeleteを意味します。

### サイクル

RED → GREEN → REFACTORの各フェーズには検証が義務付けられています。

**RED（失敗するテストを書く）**

- 1つの振る舞いに対して1つのテスト
- 明確なテスト名（振る舞いを記述）
- モックは避けられない場合のみ

書いたら必ず実行し、以下を確認します。

- テストがエラーではなく失敗（fail）すること
- 失敗理由が「機能が未実装だから」であること（タイポではない）
- テストが即座にパスする場合は、既存動作をテストしているので修正が必要

**GREEN（最小限のコードで通す）**

- テストを通す最小限の実装のみ
- オプション引数、バックオフ戦略、コールバックなどの追加はYAGNI違反

実行して、対象テストがパスし、他のテストも壊れていないことを確認します。

**REFACTOR（整理）**

- GREENの後にのみ実行
- 重複除去、命名改善、ヘルパー抽出
- テストは常にグリーンのまま維持
- 新たな振る舞いは追加しない

### 適用範囲

新機能、バグ修正、リファクタリング、振る舞い変更のすべてが対象です。例外はユーザーの明示的許可がある場合のみ（使い捨てプロトタイプ、生成コード、設定ファイルなど）。

### バグ修正とTDD

バグを発見したら、まず再現する失敗テストを書きます。テストがバグを再現し、修正後は回帰テストとして機能します。テストなしのバグ修正は許可されません。

## 5.2 テストファースト違反の検出

スキルは「合理化（rationalization）」を明示的に列挙して封じます。以下は主要な合理化パターンです（完全な一覧はスキルファイル本文に含まれています）。すべてレッドフラグとして扱われ、「コードを削除してTDDでやり直せ」というルールが適用されます。

| 合理化 | 現実 |
|--------|------|
| テストが簡単すぎる | 単純なコードも壊れる。テストは30秒で書ける |
| 後でテストを書く | 後から書いたテストは即パスするため、何も証明しない |
| 手動テスト済み | アドホックなテストは体系的ではなく、再実行もできない |
| X時間の作業を捨てるのは無駄 | 埋没費用の誤謬。検証されていないコードを残す方が技術的負債 |
| 参考として残す | 「合わせる」時点でテスト後追いと同じ |
| TDDは教条的 | TDDは実利的。テストファーストはデバッグより速い |
| 精神を守れば形式は不要 | テスト後追いは「何をしたか」、テストファーストは「何をすべきか」を検証する。同じではない |

### 完了時チェックリスト

作業完了前に以下をすべて確認します。

- 新しい関数/メソッドごとにテストがある
- 各テストが実装前に失敗するのを確認した
- 各テストの失敗理由が「機能未実装」だった（タイポではない）
- 各テストに対して最小限のコードを書いた
- 全テストがパスする
- 出力がクリーン（エラー・警告なし）
- テストは実コードを使用（モックは不可避な場合のみ）
- エッジケースとエラーケースをカバー

全項目にチェックを入れられない場合は「TDDをスキップした」ことを意味し、やり直しが必要です。

---

**要約**: TDDスキルは「失敗するテストなしに本番コードを書くな」を鉄則として強制する。先にコードを書いたら削除してやり直す以外の選択肢はない。よくある合理化パターンを明示的に列挙して封じることで、プレッシャー下での違反を防止する。
