# 第6章 デバッグと検証

systematic-debugging（根本原因の調査→パターン分析→仮説検証→実装の4フェーズ）と、verification-before-completion（完了宣言前の検証強制）。

## 6.1 systematic-debugging: 4フェーズ調査

### 鉄則

```
根本原因の調査なしに修正を試みない
```

テスト失敗、本番バグ、パフォーマンス問題、ビルド失敗など、あらゆる技術的問題が対象です。「急いでいるから」「明らかに原因がわかるから」は、むしろこのプロセスを使うべきサインとされています。

### フェーズ1: 根本原因の調査

修正を試みる前に以下を実行します。

- エラーメッセージの精読 --- スタックトレースを最後まで読む。行番号、ファイルパス、エラーコードを記録
- 再現の確認 --- 毎回再現するか。再現しなければデータ収集を続ける（推測しない）
- 最近の変更の確認 --- git diff、直近コミット、新しい依存関係、設定変更、環境差異
- 多層システムでの診断 --- コンポーネント境界ごとに入力と出力をログ出力し、どの層で壊れるかを特定
- データフローの追跡 --- 不正な値がどこで発生し、どこから渡されたかを上流に向かって追跡

### フェーズ2: パターン分析

- 同一コードベース内の動作する類似コードを探す
- 動作するコードと壊れたコードの差分を列挙する
- 「それは関係ない」と決めつけない

### フェーズ3: 仮説と検証

科学的方法に従います。

- 1つの仮説を明示的に立てる（「XがYの原因だと考える。理由はZ」）
- 最小限の変更で仮説を検証する（1変数ずつ）
- 失敗したら新しい仮説を立てる。既存の修正の上に追加しない

### フェーズ4: 実装

- 失敗するテストケースを作成（TDDスキルと連携）
- 根本原因に対する単一の修正を実装
- テストがパスし、他のテストが壊れていないことを確認

3回以上修正を試みて失敗した場合、それは個別のバグではなくアーキテクチャの問題です。修正の追加を止め、パターンの根本を問い直す必要があります。この判断はユーザーと相談してから行います。

## 6.2 verification-before-completion

### 鉄則

```
検証証拠なしに完了を主張しない
```

「テストが通るはずです」「修正しました」「問題ないと思います」はすべて禁止です。

### ゲート関数

完了を主張する前に、必ず以下のステップを踏みます。

1. IDENTIFY --- この主張を証明するコマンドは何か
2. RUN --- そのコマンドを新たに実行する（過去の結果は不可）
3. READ --- 出力全体を読み、終了コードと失敗数を確認する
4. VERIFY --- 出力が主張を裏付けるか判定する
5. CLAIM --- 裏付けがあって初めて主張する

### 主張と必要な証拠

| 主張 | 必要な証拠 | 不十分な証拠 |
|------|-----------|-------------|
| テスト通過 | テストコマンド出力: 0 failures | 以前の実行結果、「通るはず」 |
| リンタークリーン | リンター出力: 0 errors | 部分チェック、外挿 |
| ビルド成功 | ビルドコマンド: exit 0 | リンターがパスした |
| バグ修正 | 元の症状のテスト: パス | コードを変更した |
| 要件充足 | 要件リストとの1行ずつの照合 | テストがパスした |

### レッドフラグ

以下の思考パターンが出たら、検証をスキップしようとしているサインです。

- 「should」「probably」「seems to」を使おうとしている
- 検証前に「Great!」「Perfect!」「Done!」と言おうとしている
- コミットやPR作成の直前に検証を省こうとしている
- サブエージェントの「成功」報告を鵜呑みにしようとしている

このスキルは24件の失敗記録から抽出されたもので、「あなたの言葉を信じない」とユーザーに言われた事例、未定義関数がそのまま出荷された事例などが元になっています。

---

**要約**: systematic-debuggingは4フェーズ（調査→パターン分析→仮説検証→実装）で根本原因の特定を強制し、推測による修正を禁止する。verification-before-completionは「コマンドを実行し、出力を読んでから主張する」というゲート関数で、証拠なき完了宣言を封じる。
